> **Scope:** Full read-only audit of the repository at commit `2a3bb5f2` before any architectural work.

## 1. Executive summary

NTACBT is **not** a greenfield project and it is **not** a giant single HTML file at the app root — it is a **TanStack Start + Vite + React 19 + TypeScript + Tailwind v4 + shadcn/ui monorepo** whose **real product is still a 25,421-line legacy single-file app** (`public/jee-cbt.html`).

The excellent news: the React shell, routing, service/API layer, Supabase integration, PWA packaging, Android Focus-Guard app, and data pipelines **already exist**. The hard part is not "start from scratch" — it is **migrating the domain logic and rich UX out of `jee-cbt.html` without breaking a working, well-built product**.

### What is already strong (KEEP)
- Real NTA-style CBT engine (question palette, timer, sections, mark/review, on-screen calculator, autosave/resume).
- PDF → test pipeline with layered parsing (position-based => AI fallback).
- PYQ engine with baked static papers + upstream fallback + chapter/topic/mistake practice.
- Mistake notebook, chapter mastery, revision queue, analytics/mistake classification, readiness/risk model.
- Intent-aware StudyTube discovery via the `/api/public/study-planner` server route (scrapes public YouTube search, ranks by educational fit, explains "why").
- Adaptive planner with capacity, depth (crash/mastery), faculty preference, prerequisite warnings.
- Saarthi AI chat: Ollama/OpenRouter/Gemini fallback, web search grounding, rate limiting, student context.
- Supabase public test library + planner imports + anonymous score leaderboard with RLS.
- Android app with focus lock (Accessibility-based), launcher mode, reminders.
- PWA + offline caching + service worker.
- Automated validation scripts for syllabus, teachers, videos, links, analytics, JEE 2026 papers, and a robot E2E smoke test.

### The core structural problem (REBUILD)
The whole student journey lives in one 25,421-line HTML file with DOM-string rendering, global mutable state (`S`, `EX`, `route`), a bespoke router, and inline data arrays. It cannot be grown safely:
- Add a feature and the file gets harder to audit, test, and cache.
- The React shell currently does nothing but `window.location.replace("/jee-cbt.html")`.
- There are two (sometimes three) copies of academic data: `src/data/*.ts` (structured), inline `JEE_TOPICS` / `AIP_TEACHERS` in the HTML, and baked `public/pyq/*.json`.

This is the **highest-leverage** architectural issue and the reason the spec says "incremental migration, never blind rewrite."

## 4. KEEP / IMPROVE / REBUILD / REMOVE

### KEEP (working, valuable)
- NTA CBT screen, palette, timer, calculator, autosave, resume, review, scorecard.
- PDF parsing pipeline + AI Layer-6 fallback.
- PYQ practice modes and chapter/topic drill.
- Mistake classification (conceptual / formula / calculation / careless / misread / time / guess / prerequisite / incomplete knowledge).
- Mastery engine states and revision queue.
- StudyTube intent-aware discovery + ranking + explainability.
- Adaptive planner with capacity and depth.
- Saarthi AI chat (context, rate limiting, fallback, web grounding).
- Live class finder.
- Public test library + leaderboard.
- Android Focus Guard app.
- Validators / robot smoke.

### IMPROVE (works, needs refactor)
- **De-duplicate data**: one TS source-of-truth consumed by the legacy HTML and any new React route.
- **Add schema versioning** to `localStorage["jeecbt.v1"]` and migration path.
- **Make the reactive React shell real**: at minimum route-level pages for `Dashboard`, `Planner`, `StudyTube`, `PYQ`, `CBT`, `Analytics`, `Focus`, `Saarthi`; lazy-load the legacy page for deep features initially.
- **PWA precache is broken**: VitePWA generated a SW but the production payload lands in `.output/public` (Nitro), not `dist`, so the precache manifest is empty (build warning: `precache 0 entries`). Runtime caching still works after first load; fix the build-time precache.
- **Teacher metadata**: add language, style, coverage, last-verified.
- **Validation**: validators are mostly "does the string exist" checks; make them structurally validate the baked public data too.

### REBUILD (fundamentally limiting)
- The single HTML file architecture for the product surface. Migrate into feature routes incrementally while keeping `/jee-cbt.html` alive as the compatibility fallback.
- The bespoke in-HTML `ROUTES` router + DOM-string rendering layer. New screens should use TanStack Router + React.
- The giant `S = load()` global state object. Introduce a typed, versioned client store (localStorage adapter) and use it in new screens first.
- Duplicated academic datasets (inline `JEE_TOPICS`, `AIP_TEACHERS`, `src/data/*.ts`). Collapse to one typed source-of-truth with a generator/validation bridge.

### REMOVE (only after safe replacement)
- Nothing yet. Do **not** remove `jee-cbt.html` in the near term. It is the working product. It should become a compatibility fallback/legacy view, then be retired only after feature parity in React.

## 5. Critical bugs / issues found

1. **PWA precache is empty.** Build output shows `precache 0 entries` and `One of the glob patterns doesn't match any files`. The SW lives in `dist` while the app payload is in `.output/public` (Nitro). Offline works only via runtime caching after first visit.
2. **React shell is a redirect stub.** `/` does `window.location.replace("/jee-cbt.html")`; no React feature route exists yet, which is the core migration blocker.
3. **Two sources of truth for syllabus/teachers.** `src/data/syllabus.ts` is unused; the planner uses inline legacy data. Any syllabus change needs edits in two places.
4. **`build-cbse-syllabus.mjs` depends on external `pdftotext`** and is not wired into `npm run build`, so a fresh deploy may not have the CBSE JSON.
5. **`public/pyq/` is gitignored** and regenerated on each build; if the upstream HF dataset or pinned Samkarya repo changes/unavailable, coverage is whatever was last baked. The fallback API mitigates but keeps a large in-memory dataset on the server.
6. **LocalStorage has no schema migration.** `jeecbt.v1` is a single blob; forward changes can silently corrupt old users' data.
7. **No automated test for the critical student journey in the new React shell.** `scripts/robot-test.mjs` exists but presumably drives the legacy page; new routes need their own coverage.
8. **`src/routes/index.tsx` meta title still says "Someshwar JEE Main CBT Platform"**, while the product brand per repo is NTACBT; branding is inconsistent across README, metadata, manifest, and HTML title.

## 6. Data integrity risks

- **Academic data source-of-truth not enforced.** Official syllabus, verified educators, derived mastery, and AI-generated explanations currently flow through loosely-typed objects with no category tag. Risk of silent mixing.
- **Legacy inline data vs structured data drift** (JEE_TOPICS vs syllabus.ts).
- **PYQ provenance is third-party**, not NTA-official; per-question verification status is absent.
- **Subjective question metadata** (difficulty, weightage) is approximate and unverifiable; the app already marks some as approximate but should make the caveat visible.
- **Transcribed user 2026 papers** are committed JSON derived from OCR; they should be explicitly tagged `source: user-provided scans, verification: provisional`.

---

## 7. Performance & mobile risks

- 1.06 MB `jee-cbt.html` (gzip much smaller, but still a single large document + inline JS). On a budget Android phone this is a one-shot giant parse.
- DOM-string rendering + re-render on every navigation; acceptable in legacy, but new screens should use React reconciliation and `virtualized` lists for PYQ/palette.
- `public/pyq/` papers are small (~50KB each) so the baking approach is good.
- Charts use custom canvas in legacy; Recharts is available in the React shell for the new analytics screens.
- Lazy-load has not been used for the legacy page because the shell is a redirect. New routes should be route-split.

## 8. Security audit

**Good (already present):**
- `api/public/study-planner`, `live-classes`, `pdf-reformat`, `ai-chat` are **server-only** and never expose API keys.
- `cloud-config` only returns the Supabase **publishable** key, never the service role.
- `client.server.ts` service-role client is server-only; `auth-middleware` rejects missing/malformed bearer tokens.
- AI chat + PDF reformat have in-memory per-IP rate limits.
- No client-side secrets in `public/jee-cbt.html` (YouTube is scraped server-side; Gemini/OpenRouter keys are server env).
- CSRF middleware is installed for serverFns.

**Needs attention:**
- `supabase` public RLS currently allows anon `INSERT`/`UPDATE`/`DELETE` on `public_tests` and `planner_imports`; the in-app "admin password" is the only gate. This is deliberate for a single-owner app, but must change before any real multi-user build.
- In-memory rate-limit maps (AI, PDF, live, study-planner) are per-instance and unbounded-ish (they cap to 2000/500/24 entries — good, but not shared across instances).
- The `study-planner` and `live-classes` routes scrape YouTube public search pages. This is a ToS/robots risk to document; it is not circumventing DRM, but is third-party scraping and can break without notice.
- `build-cbse-syllabus.mjs` pulls official PDFs at build time (fine) but uses `pdftotext` — a toolchain dependency to document.
- Legacy HTML accepts arbitrary uploaded PDFs and uses the AI fallback; content is not persisted server-side except via Supabase `public-tests` storage. It should enforce upload size/type limits (currently policy only checks extension).

## 9. Testing / observability

- **Existing:** `validate:jee2026`, `validate:syllabus`, `validate:teachers`, `validate:videos`, `validate:links`, `validate:analytics`, `validate:all`, `robot-test`.
- **Coverage gaps:** no unit tests for the new data layer, no integration tests for server routes (YouTube/Supabase faults, AI unavailable), no E2E for the full journey in React, no failure-case tests (no internet, unavailable video, malformed PDF, invalid data, expired session).
- **Observability:** `error-capture`, `error-page`, `reportLovableError` exist; but no recommendation-failure diagnostics, no academic-data health endpoint, no slow-page monitoring beyond what the platform provides.

## 11. Recommended execution order (derived from spec, adapted to this codebase)

- **Phase 1 (foundation):** shared academic source-of-truth (`src/features/academics`), typed exam/year isolation, client-store schema/versioning, route skeleton (`/app/*`) that lazy-mounts the legacy app as a fallback.
- **Phase 2 (academic SOT):** collapse inline data into generated/bridged data; add `validate:sot`; add provenance/verification tags; expose official syllabus in the React sidebar.
- **Phase 3 (StudyTube):** a React StudyTube shell that reuses `/api/public/study-planner`; Study Theater (video + workspace tabs) as a route.
- **Phase 4 (CBT + analytics):** React CBT route wrapping the existing engine, then new analytics/mistake-doctor UI using Recharts.
- **Phase 5 (planner):** React planner consuming SOT + mastery + availability.
- **Phase 6 (Saarthi):** contextualized chat with teaching sequence (hint → guidance → explanation → verification).
- **Phase 7 (Focus):** mission/Focus bridge.
- **Phase 8 (polish):** animations, PWA fix, perf, dark-mode audit.
